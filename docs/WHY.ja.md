# なぜこの形なのか

[English](WHY.md)

ここにある決まりはどれも、先に試したやり方が失敗して置き換わったものです。決まりを変えるときは、先になぜあるのかを読んでください。

## なぜ「NOW」（今の状態の文書）を作らないのか

最初はチームごとに `NOW.md`（「今ここまで来ている」）がありました。区切りごとに書き直し、新しいセッションには毎回これを渡していました。うまくいかなかったのは 3 つです。

1. **書き直すあいだに古くなる。** 書き直すのは区切りのときだけで、作業はいつも動いています。次のセッションは、もう正しくない所も含めて丸ごと信じました。
2. **長くなる。** 書く人はそれぞれ大事だと思うことを足し、あまり消しません。読むたびにトークンが増え、大事な 1 行は真ん中に埋もれました。
3. **2 つ目の写しになる。** 決定が会話にも NOW にも、ときには憲章にもあり、写し同士が食い違いました。

いまは、状態を「作業そのものが変える場所」にだけ置きます。決定は `decisions.md` の 1 行、仕事の状態はそのファイルの先頭 3 行、誰がどこにいるかは `teams.tsv` の 1 行。別に合わせておくものも、引き継ぐものもありません。

## なぜ仕事ファイルの先頭 3 行なのか

- **直すのが安い。** 状態を変えるのは 1〜3 行を直してコミットするだけなので、誰も後回しにしません。
- **スクリプトが読める。** 位置とラベル（`Status:` / `Owner:` / `Waiting on:`）が決まっているので、`status.sh` は中身を理解しなくても読めます。
- **1 つのファイルで 2 役。** 同じファイルがメンバーへの指示書（4 行目から）と仕事の状態（1〜3 行目）なので、両者がずれません。
- **崩れた先頭は見えたままにする。** 3 行が欠けていたり、`Status` が `active`・`waiting`・`done` 以外だったりするファイルは `unknown` として一覧に残し、警告に名前を出します。最初の版はこれを「済み」と数えていました。見た目は片付きますが、誰も見ていない仕事ほど隠れてしまいました。

## なぜ状態を LLM で作らないのか

「全部読んで、今どうなっているか教えて」とモデルに頼むのは簡単です。それをしない理由は次のとおりです。

- **毎回違う。** 同じことを 2 人が聞いたら、同じ答えが返るべきです。
- **毎回トークンがかかる。** 状態は、いちばん何度も見るものです。
- **もっともらしく間違える。** モデルはすき間をそれらしいもので埋めます。決まった形を読むスクリプトは、間違えるときも目に見える形（「decisions.md が無い」）なので、何を直せばいいかが分かります。
- **すぐ出る。** 小さな組織で約 0.5 秒（実測。動いているメンバーを Claude Code に聞く時間も含む）なので、気軽に何度でも見られます。

## なぜリーダーは監督だけなのか

自分でもコードを書くリーダーは、すぐに全体を見失います。コンテキストが差分やエラーで埋まり、ほかのメンバーが何をしているかを忘れ、コンテキストが尽きると計画も一緒に失われます。計画・指示書・メンバーの立ち上げ・確認・決定の記録だけをするリーダーは:

- 1 つのコンテキストでずっと長く働ける
- きれいに交代できる（知っていることは全部、3 種類のファイルにすでにある）
- 1 つずつ自分でやる代わりに、何人ものメンバーを同時に動かせる

コード・文章・調査・動画などの作業はメンバーに渡します。指示書 1 つにつき 1 人、それぞれ自分の worktree で。

## なぜ決まりを文章ではなく hook にするのか

「PR は、私が試して OK を出してから」は、指示に書き、メモリに書き、もっと強く書き直しました。それでも 3 回とも破られました。逆らったわけではありません。長いセッションでは、何時間も前に読んだ決まりより、癖（「できたから PR を出そう」）が勝つのです。

hook（`hooks/human-gate.sh`）はシェルのコマンド（と、matcher に足した道具）の前に毎回動くので、セッションがどれだけ長くても、よくある誤操作を止めます。鍵ではなく安全網です。よくある書き方は止めますが、あらゆる書き方を止めるわけではありません（止められないものは `hooks/README.md` に書いてあります）。大事な点が 3 つあります。

- **解除には本物のターミナルが要る。** `human-ok.sh` は対話のターミナルでないと動きません（Claude Code の道具には無い）。hook は解除のファイルを書くコマンドも止めます。だからセッションが、癖やうっかりで自分を承認することはありません。
- **解除は 1 つのリポジトリの 1 つのブランチに。** ブランチ名だけ（「main」「fix/login」）だと、たくさんのリポジトリにあります。最初の版では、OK がその全部に効いていました。
- **解除には期限がある**（既定で 6 時間）。OK は、あなたが見た変更に対してのもので、その後ブランチがどうなったかに対してではありません。

hook と組にして、文章の決まりを 1 つだけ全メンバーに渡します。「止められたコマンドを、別の書き方でやり直さない。報告する」。これが無いと、止められたセッションは同じことをする別のコマンドを探しがちです。

hook は、早すぎると本当に時間やお金がかかる少しのことだけに使ってください。止める所はどれも手で解除する所なので、少なく保ちます。

## なぜ worktree を決まった 1 か所に置くのか

リーダーもメンバーも、それぞれ自分の git worktree で作業するので、互いに上書きしません。最初は worktree をアプリのフォルダの中（`.claude/worktrees/`）に作っていました。アプリの自動の片付けが、そのいくつかをコミット前の作業ごと消しました。

いまは、すべての worktree を自分で決めた 1 つの置き場（`WORKTREE_ROOT`・`.claude/` の外。片付けが届かない所）に作ります。`member-launch.sh` はほかの場所を拒み、`status.sh` は警告を出します。おまけに `ls "$WORKTREE_ROOT"` で、進行中のものが全部見えます。

## なぜメンバーのアカウントを 1 か所で決めるのか

メンバーは、立ち上げたセッションとは別の Claude のアカウントで動くことがあり、人によってアカウントも違います。立ち上げるたびにアカウントを選んでいたころは、メンバーが違うアカウントで動きました。使える量が尽きる、つなぎ先が無い、様子を見る人から見えない。しかも、分かるのはずっと後でした。

いまは設定が 1 つ（`org.env` の `MEMBER_CONFIG_DIR`）です。`member-launch.sh` はこれが無いと立ち上げず、毎回アカウントを表示してから立ち上げます。並行で入るもう 1 人は、共有の設定を書き換えずに、そのコマンドの前に自分のフォルダを付けます。

## なぜ指示書をコミットしてからメンバーを出すのか

コミットしていない指示書で始めたメンバーは、リーダーが後で直す前の版を読むことがあります。するとリーダーは、メンバーが見ていない文で確認することになります。コミットした指示書なら、メンバーもリーダーも `status.sh` も同じ文を読みます。

コミットするのは**リーダーの**作業フォルダで、メンバーの worktree はそのコミットから作ります。指示書をメンバーの worktree にだけ書いたときは、リーダーの作業フォルダを読む `status.sh` にその仕事が出ず、一覧から消えていました。

## なぜ入るのは 1 行なのか

書いた引き継ぎ書は、毎回どこかが抜けていました。worktree の場所、ブランチ、アカウント、まだ動いているメンバー。引き継ぎ書を上手に書く代わりに、入ることそのものを手順（`JOIN.md`）にして、事実はすでにある場所から読むようにしました。渡すのは 1 行だけです。「このリポジトリの JOIN.md を読んで、そのとおりにやって」。
